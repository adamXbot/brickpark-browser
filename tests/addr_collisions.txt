# The address collisions a lane has RULED ON -- the baseline for the
# `addr_sweep` ctest. Two row kinds:
#
#   NAME <name> <addr>,<addr>...            one name, several addresses
#   ADDR <addr> <name>=<size>,<name>=<size> one address, several names whose
#                                           declared sizes disagree
#
# The class (docs/lanes/scope-port-p3.md §3.3, docs/lanes/scope-port-a10.md §1):
# on x86 each TU's `extern` only says "an object of this type lives somewhere"
# and the real linker resolves each spelling to the address its own .obj
# recorded, so two files really can mean two different objects by one name. The
# portable build has no .obj: `gen_link.py` plans ONE storage object per name,
# so the two spellings collapse and every TU that spelled the loser is sheared
# by the difference. The bytes VC6 emits are identical either way, so audit.py,
# relocs.py, match.py and verify.py are blind to this and always will be.
#
# The gate:
#
#   * a row NOT here, or a row that GREW a new address / changed a size -> FAIL;
#   * a row here that is no longer reported -> passes and prints FIXED; drop the
#     row in the same commit as the fix.
#
# That last rule is why this file can hold PORT-P3's open findings today and
# stay green the moment PORT-M15 renames them.
#
# Measured 2026-09-12 by PORT-A10 on 25005b2c: 18 NAME rows (PORT-P3's 17 plus
# `Track_Update`, which PORT-M7 had already mitigated), 5 ADDR rows.
#

# address `gen_link` actually emits (the "winner" column of PORT-P3 §3.3) and
# what the losing TU therefore reads. LEGOLAND/*.c is PORT-M15's to edit.
